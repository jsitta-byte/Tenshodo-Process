# Current-State Discovery Assessment

## Purpose

Provide a structured client-wide assessment after initial evidence intake and before detailed transformation design.

This is descriptive discovery, not a maturity score or target-state verdict.

## A. Working planes

For each collaboration/work surface:

| Surface | Purpose | Primary users | Information classes | Current authority? | Known duplication/conflict | Notes |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |

Questions:

- Where do people actually do recurring work?
- Which working surfaces are formally sanctioned?
- Which are shadow/informal?
- Which content classes exist in multiple editable places?
- Which working planes would be disrupted by forced migration?

## B. Durable-state capability

For material recurring work, determine whether the organization can durably answer:

- [ ] What is the current task/state?
- [ ] What is complete?
- [ ] What remains?
- [ ] Who/what may execute the next action?
- [ ] What is the exact next action?
- [ ] What evidence proves completion?
- [ ] What external sources must be revalidated?
- [ ] Can a zero-context successor resume?
- [ ] Are interruptions/retries recoverable without repeating work?
- [ ] Is there a durable decision/history trail?

Record examples of:

- strong durability;
- context trapped in people/chat;
- stale trackers;
- orphaned projects;
- repeated reconstruction.

## C. Authority and truth

For material information/decision classes:

| Class | Current source | Claimed authority | Current decision authority | Conflicts / ambiguity | Validation required |
|---|---|---|---|---|---|
|  |  |  |  |  |  |

Look specifically for:

- dual canonical sources;
- undocumented approval practices;
- target roles mistaken for current authority;
- key decisions dependent on individual habit;
- material authority inferred only from title.

## D. Current processes

Identify high-value recurring processes and capture:

- trigger;
- major steps;
- primary actors;
- systems;
- handoffs;
- approvals;
- evidence/output;
- exception paths;
- pain points;
- hidden/manual work;
- frequency;
- consequence of failure.

Do not require polished process maps at this stage.

## E. Process/change pain

Look for:

- repeated re-entry/reconciliation;
- slow handoffs;
- missing current state;
- unclear ownership;
- approval bottlenecks;
- changes with surprise downstream impact;
- unmanaged spreadsheets;
- duplicated data;
- frequent rework;
- repeated context loss;
- work that cannot survive employee absence.

### Control questions

- Is authoritative input declared?
- Are outputs validated?
- Can an AI output become binding without human review?
- Are prompts/agents versioned?
- Are consequential workflows checkpointed?
- Is failure/rollback defined?
- Can AI activity be audited?
- Are employees clear about authority boundaries?

### Candidate incubation opportunities

List functions where AI could safely perform build/propose work before a permanent human steward exists.

Do not recommend AI incubation merely because a function lacks staff.

## G. Confidentiality and access

Record:

- allowed systems;
- prohibited systems;
- data categories requiring special handling;
- retention/export restrictions;
- client repository visibility;
- consultant access expiry;
- secrets/credential rules;
- whether sanitized methodology lessons may be retained;
- contractual limitations on reusable IP.

## I. Candidate pilot areas

For each candidate:

- problem;
- current durability gap;
- current authority;
- relevant systems;
- available evidence;
- likely benefit;
- material risks;
- discovery gaps that must close first.

## J. Assessment output

The assessment should end with:

1. discovery mode confirmation;
2. highest-consequence unknowns;
3. targeted validation queue;
4. recommended pilot candidates;
5. control-plane bootstrap inputs;
6. exact next action.

Do not convert this assessment into a target-state design until the discovery output contract is satisfied.
